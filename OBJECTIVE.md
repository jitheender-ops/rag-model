# Objective & requirements

**Objective.** A voice-in, answer-out RAG system over `ai4bharat/MSMARCO-XI` (Hindi, Tamil,
Bengali, English) that answers a spoken question from retrieved context in **under 200 ms of
owned compute**, refuses when it should, and publishes the measurement for every claim it makes.

**Scope of the 200 ms.** `t0` = the server receives the STT `is_final` event. `t1` = the last
answer token is flushed, after the grounding verdict. STT and TTS are vendor round-trips outside
that window — they are **measured and published beside it** (`data/excluded_legs.json`), never
folded into the total. See [README.md](README.md#d2--the-200-ms-window) for why the line is drawn there.

Every number below is regenerated by one make target. Report headers stamp machine, embedder,
seed, and commit.

## Tool calling (requirement 5)

`search_corpus(query, lang, k)` — the generator's one tool, for the case the rest of the path
cannot fix: retrieval put the answer outside the top passages and the model can see that what
it was handed does not answer the question.

| limit | why |
|---|---|
| one hop, enforced by dropping `tools` from the request body | not a prompt request the model can overrule; unbounded hops make it an agent loop |
| shares `fuse()` with `retrieve()` | a second ranking would append passages not comparable to the context they join |
| numbering continues across the hop | a citation into a tool result still resolves to a real chunk id, so gate 4 verifies against the right passage |
| every failure returns a tool message | unknown tool, bad arguments, a search that raises — the answer falls back to the context already held |

Measured on `openai/gpt-oss-20b`: **1 hop / 1126 ms** when the context does not answer,
**0 hops / 269 ms** when it does. Not calling the tool is the behaviour that had to be
engineered — the prompt's rule 3 is replaced, not extended, in the tool variant.

## The four gates (requirement 6)

| gate | fires on | cost |
|---|---|---|
| 1 | unsafe request, prompt injection | before retrieval — **0.05 ms** |
| 2 | retrieval score below a floor swept on a held-out set | after retrieve |
| 3 | injected instructions inside a retrieved chunk | context sanitised, answer continues |
| 4 | answer not grounded in the passage it cites | after generate |

Neither floor is fitted on the set that grades it. `make calibrate` refits both whenever an
upstream stage moves.

## Reproducing

```bash
make venv && make corpus     # once
make check                   # 23 self-checks, no model, no network, ~5 s
make submit                  # chunking → calibrate → guardrails → latency, ~30 min
make serve                   # browser demo: hold to speak, localhost:8000
```

## Two things stated rather than buried

1. **Answer generation does not fit in 200 ms.** Four LLM providers are wired and measured
   (`make llm-probe`): the fastest, Groq llama-3.1-8b, is 161 ms P50 against 152 ms of room —
   and on real multilingual passages it serves **0 / 30** requests inside the budget. So
   `GENERATOR=extractive` is the default: the answer is a sentence lifted from the cited
   passage, grounded by construction. An LLM becomes viable north of 500 ms; both paths are
   harnessed identically and the choice is one env var.
2. **The 0% hallucination rate is the least interesting number here.** An extractive generator
   is supported by construction. The real failure mode is citing a real passage that does not
   answer the question — gate 4's job, and a lexical verifier catches only ~9% of those at its
   false-abstention budget. An NLI cross-encoder is the named upgrade and the highest-value
   swap in the repo.

3. **The 200 ms PASS is measured on 1200 passages / 12,024 chunks.** `dense + bm25 + rrf` is
   the one row of six that is linear in corpus size; at 8.8M passages it is the stage that
   ends the budget. That is now a configuration change rather than a rewrite: `INDEX=hnsw`
   builds a real faiss graph behind the same `Index.search()`, and `make ann` measures both
   backends across a 16× range — exact grows 19×, the graph grows 3×, and the graph returns
   99.9% of exact's top-50. Exact remains the default because at this size the graph saves
   0.15 ms of a 48 ms request, which is inside the noise.

4. **Gate 4's NLI upgrade was built and rejected on its own evidence.** It is worse in both
   directions at once — 78% vs 84% correct abstention, 9.2% vs 3.8% false abstention, and
   43% vs 57% on near-miss, the bucket it was meant to fix — and its P100 breaks the budget.
   The default did not change. See [reports/verify.md](reports/verify.md).
